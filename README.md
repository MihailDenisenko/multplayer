# 📜 Чепуха — многопользовательская 3D браузерная игра

## Как считаются загибы

Число загибов — лимит каждого листка отдельно. Одна успешная отправка
считается одним загибом этого листка, независимо от количества записей
в ходе и от того, вернулся ли листок к автору. Например, 13 загибов при
трёх листках означают 39 принятых отправок суммарно. На последнем загибе
листка игрок пишет только ответ. Готовый листок больше не передаётся,
а остальные продолжают двигаться. Игра заканчивается, когда готовы все листки.

Счётчик текущего листка и число готовых листков видны на игровом экране.
Комната сериализует отправки на сервере, чтобы повторные действия
не превышали лимит листка.

Экраны адаптированы для телефонов: отдельная панель ввода, динамическая
высота при экранной клавиатуре, безопасные отступы, крупные элементы управления.

## Запуск на этом компьютере (Windows)

Установленный PostgreSQL 15 используется для отдельного экземпляра игры на
`127.0.0.1:5433`. Данные находятся в `.local/postgres`, случайный пароль —
в `.env.local`. Эти файлы исключены из Git. Существующий PostgreSQL на 5432
не используется. Не удаляйте `.local/postgres`, если хотите сохранить партии.

```powershell
npm.cmd run db:start
npm.cmd run db:push
npm.cmd run build
npm.cmd start
```

Сервер открывается на `http://localhost:3000`. В другом терминале запустите:

```powershell
npm.cmd run tunnel
```

Команда выводит временную HTTPS-ссылку `lhr.life` через localhost.run, проверяет
её доступность каждые 10 секунд и переподключается при потере доступа.
Текущее состояние хранится в `.local/tunnel.json`; зал ожидания получает
обновлённый адрес через `/api/connection` без перезапуска сервера.
Устаревшие временные адреса из `.env.local` больше не используются.
Создайте комнату и нажмите «Скопировать ссылку»: гость откроет приглашение
с уже заполненным кодом комнаты. Для старта нужны минимум три игрока. Компьютер, сервер и туннель
должны оставаться включёнными. При перезапуске туннеля ссылка меняется.
Старые временные ссылки после отключения не восстанавливаются: ведущий
должен скопировать обновлённое приглашение. Для неизменного адреса нужен
постоянный хостинг или домен; для такого адреса можно задать `PUBLIC_APP_URL`.
Остановка туннеля: `npm.cmd run tunnel:stop`.
Ведущий может нажать «В главное меню» в зале ожидания и создать другую комнату.
Для туннеля используется встроенный Windows OpenSSH, отдельная установка не нужна.
Вебхук и WebSocket для текущей игры не требуются: используется HTTP polling.

Проверка полного цикла игры через API: `node scripts/smoke.cjs`.
Проверка внешнего адреса: задайте переменную `TEST_BASE_URL` перед этой командой.
Проверка создаёт тестовую комнату и удаляет только её после завершения.
Остановка базы: `npm.cmd run db:stop`.

Классическая настольная игра «Чепуха» (складная бумага с вопросами и ответами),
реализованная как полноценное fullstack-приложение: 3D-сцена на Three.js,
игровая логика на сервере, состояние — в PostgreSQL через Drizzle ORM.

## ⚠️ Адаптация архитектуры под требования окружения

Исходное ТЗ описывало отдельный `Node.js + Express + socket.io` сервер и
отдельный статический клиент (`/server`, `/client`). Проект, однако,
разворачивается в стандартном шаблоне **Next.js App Router**, который
собирается и стартует через `next build` / `next start`, без возможности
поднять произвольный WebSocket-сервер рядом (и без модификации
`package.json`). Поэтому архитектура была адаптирована с сохранением всей
игровой логики и 3D-опыта:

- **Сервер** → API-роуты Next.js (`src/app/api/...`) + PostgreSQL (Drizzle).
  Вся логика комнат/листков/раундов, которая в ТЗ была в `gameManager.js` /
  `roomManager.js`, перенесена в `src/lib/game/*` и соответствующие роуты.
- **Реальное время** → вместо WebSocket используется последовательный HTTP-polling
  (примерно два запроса в секунду, без перекрывающихся запросов; `GET /api/rooms/[code]/state`). Для пошаговой игры вроде
  «Чепухи» обычная задержка меньше секунды и не влияет на игровой процесс, а решение
  полностью укладывается в инфраструктуру, которую валидирует платформа
  (`next build` → `next start` → `/api/health`).
- **Защита от подглядывания** сохранена: сервер никогда не возвращает текст
  загнутых частей листка — только текущее ключевое слово. Весь текст
  раскрывается лишь в финале (`/api/rooms/[code]/results`), когда статус
  комнаты переходит в `finished`.
- **3D-клиент** реализован на Three.js как клиентский React-компонент
  (`src/three/*`, подключается в `src/components/GameScreen.tsx`) —
  ровно так, как и предполагалось в ТЗ.

## Структура проекта

```
src/
├── db/
│   ├── schema.ts            # Таблицы rooms, players, sheets, entries (Drizzle)
│   └── index.ts             # Подключение к PostgreSQL
├── lib/game/
│   ├── logic.ts             # Чистые функции: коды комнат, направление, стадии хода
│   ├── types.ts             # Общие DTO-типы клиент/сервер
│   ├── server.ts            # Серверные хелперы: сборка состояния, авторизация по токену
│   ├── client.ts            # Клиентские fetch-обёртки + сессия в localStorage
│   └── avatar.ts            # Обрезка аватарки в круг на canvas
├── three/
│   ├── sceneManager.ts      # Оркестратор сцены: камера, свет, стол, анимации
│   ├── paperSheet.ts        # Класс листка бумаги: CanvasTexture + анимация загиба
│   ├── handAnimator.ts      # 3D-руки: idle / writing / folding / passing / receiving
│   ├── tableScene.ts        # Стол, окружение, карточки игроков (аватар + статус)
│   └── soundManager.ts      # Синтезированные через Web Audio звуки (без файлов-ассетов)
├── components/
│   ├── GameApp.tsx          # Роутинг экранов + поллинг состояния
│   ├── HomeScreen.tsx       # Вход: имя, аватар, создание/подключение к комнате
│   ├── WaitingRoom.tsx      # Лобби с настройками и списком игроков
│   ├── GameScreen.tsx       # 3D-сцена + игровой UI (вопрос → ключевое слово → передача)
│   └── ResultsScreen.tsx    # Финальное разворачивание листков
└── app/
    ├── api/rooms/...        # REST API комнаты/лобби/игры
    └── page.tsx             # Точка входа
```

## Игровой процесс

1. **Лобби.** Ведущий создаёт комнату (код из 6 символов), настраивает:
   количество игроков (4–10, минимум для старта — 3), число загибов
   (рекомендуется 10–15; больше загибов — длиннее партия), направление
   передачи (по/против часовой стрелки), визуальный
   стиль (реалистичный / мультяшный) и показ имени первого автора.
2. **Игра.** Каждый игрок видит свой лист от первого лица: стол, аватарки
   других игроков со статусами («Пишет…», «Ожидает», «Готово ✓»,
   «Не в сети»), поле ввода снизу экрана. Цикл хода:
   вопрос → ключевое слово → загиб+передача (первый ход); либо
   ответ → новый вопрос → ключевое слово → загиб+передача (средние ходы);
   либо только финальный ответ (последний ход). Анимации загиба и передачи
   реализованы как 3D-твины (сворачивание верхней части листа, полёт листка
   к соседу) с синтезированными звуковыми эффектами.
3. **Финал.** Когда каждый листок достиг лимита загибов, игра завершается, и каждый
   игрок может пролистать все получившиеся абсурдные диалоги
   («Следующий/Предыдущий листок»), начать игру заново.

## База данных

Таблицы (`src/db/schema.ts`): `rooms`, `players`, `sheets`, `entries`.
Листок хранит текущего держателя (`currentHolderId`) и флаг
`isActiveForHolder` — это позволяет моделировать очередь, если игрок
работает медленнее соседей и к нему "прилетает" второй листок раньше, чем
он закончил первый.

Применение схемы: `npx drizzle-kit push` (использует `DATABASE_URL` из `.env`).

```bash
npm install

npm run start
```
